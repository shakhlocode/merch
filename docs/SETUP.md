# Своя копия Uzum Merch

Фронтенд и серверные маршруты сохранены из переданного репозитория. Недостающая
база восстановлена из описания таблиц и контрактов кода. Это новая независимая
копия, а не экспорт старого проекта. Старые аккаунты, товары, фото и заказы в неё
автоматически не попадут.

## 1. Создать Supabase

В своём аккаунте Supabase нажмите **New project**, выберите свою организацию,
назовите проект `uzum-merch`, задайте уникальный пароль БД и выберите подходящий
регион. Пароль сохраняйте в менеджере паролей, не в GitHub и не в чате.
Дождитесь завершения создания проекта.

Откройте **SQL Editor → New query** и выполните целиком
все SQL-файлы из `supabase/migrations/` по порядку имён, каждый отдельно.
Это скрипты для пустого проекта:
не применяйте его к старой рабочей базе и не запускайте второй раз. При ошибке
транзакция откатится; сначала выясните причину. Скрипты создают 14 таблиц,
функции, триггеры, права доступа и публичный бакет `merch-products` для фото.
Скрипт не удаляет и не пересоздаёт системные схемы Supabase Auth/Storage.

В настройках API проекта скопируйте Project URL и публичный ключ `anon`
(legacy anon key). Код использует `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
Не используйте `service_role`/secret key: публичный ключ попадёт в браузер,
доступ к данным ограничивается RLS и правами на функции.

## 2. Подключить Vercel

Сначала сохраните изменения этого репозитория в своей копии GitHub.
В своём Vercel выберите **Add New → Project**, импортируйте свою копию
репозитория; framework — Next.js, root directory — корень репозитория.
Команда сборки `npm run build`; Node.js 24.x. Не отключайте проверку TypeScript.

В Environment Variables задайте:

- `NEXT_PUBLIC_SUPABASE_URL`: Project URL нового Supabase.
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`: публичный anon key нового Supabase.

Нажмите Deploy. Полученный домен задайте в `NEXT_PUBLIC_APP_URL`
в виде `https://адрес-сайта` без пути, затем выполните Redeploy.
Переменные `NEXT_PUBLIC_*` встраиваются во фронтенд при сборке, поэтому
их изменение требует новой сборки.

В Supabase **Authentication → URL Configuration** укажите адрес сайта как
Site URL и добавьте Redirect URLs с этим же доменом:

```text
https://адрес-сайта/auth/callback
https://адрес-сайта/auth/hash-callback
```

Для локальной разработки добавьте также:

```text
http://localhost:3000/auth/callback
http://localhost:3000/auth/hash-callback
http://127.0.0.1:3000/auth/callback
http://127.0.0.1:3000/auth/hash-callback
```

Включите Email provider и создание пользователей для первого входа по письму.
Для приглашений на произвольные корпоративные адреса настройте собственный
SMTP в Supabase. Стандартная отправка Supabase имеет ограничения по получателям
и частоте; она не заменяет рабочую почтовую интеграцию. Секрет SMTP хранится
в Supabase. Для preview-доменов разрешайте только нужные адреса своей команды.

## 3. Первый администратор

Откройте свой сайт, выберите вход по письму и укажите `shahlo.kham@gmail.com`.
Подтвердите вход и установите пароль. Для создания аккаунта через Dashboard
Authentication → Users убедитесь, что пользователь подтверждён и может войти;
пароль должен быть личным, не тестовым паролем коллеги.

После создания пользователя выполните в SQL Editor
`supabase/bootstrap-admin.sql`. Он назначает администратором только указанный
email. Затем обновите страницу сайта; откройте `/admin`.
Если создавали аккаунт вручную и он пока не устанавливал пароль через сайт,
пройдите `/set-password`, чтобы заполнить `password_set_at`.

В админке добавьте кадровый справочник, товары, варианты размеров и цветов,
а также поступления на склад. Для права на заказ сотрудник должен быть активен
и иметь реальную дату найма не менее трёх месяцев назад. Статус администратора
сам по себе не освобождает от этих правил заказа. Начальная база пуста: это
нормально. Категории можно добавить в таблицу `categories` через Dashboard.
Фото загружаются из редактора товара в созданный бакет.

## 4. Редактировать и сразу проверять

Проверенная среда: Node.js 24.19.0, npm 11.9.0. Для локального запуска:

```bash
npm ci
cp .env.example .env.local
# Заполнить .env.local значениями своего проекта.
npm run dev
```

В средах с обязательным HTTPS-прокси установщик Supabase CLI требует:

```bash
npm_config_https_proxy="$HTTPS_PROXY" npm ci
```

Для полностью локального Supabase нужны Docker и установленный CLI:

```bash
npx supabase start
```

Используйте локальный URL и локальный anon key из `supabase status`,
не публикуйте остальные ключи из его вывода. CLI применяет миграцию при
первом запуске. Живые процессы необходимо запускать заново в новой задаче;
используйте имеющийся checkout, не создавайте Git worktree без необходимости.

Изменения интерфейса автоматически обновляются локально. Коммиты в основную
ветку запускают сборку Vercel; отдельные ветки дают preview-деплои.
Preview лучше подключать к отдельной тестовой БД.

## Проверки

```bash
npm run db:build
npm run db:test
npm run build
npm run lint
```

`db:test` использует одноразовый PostgreSQL 17 в Docker без опубликованных
портов. Тестовый каркас предоставляет системные роли и минимальные таблицы
Auth/Storage; сами таблицы приложения, SQL-функции и RLS настоящие. Этот тест
не заменяет проверку отправки письма, браузерной сессии и Storage API на Supabase.

На опубликованном сайте проверьте первый вход по письму, создание пароля,
обычный вход, каталог, заказ, личные заказы, запрет доступа к чужим данным,
админку, поступление товара, отмену и выдачу заказа, загрузку фото.

## Что восстановлено, а что неизвестно

Обновлённый процесс Code 128, выдачи и редактирования состава описан в
[HANDOUT.md](HANDOUT.md). Он дополняет первоначальное восстановление ниже:
офисная выдача теперь доступна только сканированием готового заказа;
ручное завершение оставлено для удалённых заказов.

- Оригинальные страницы и серверные обработчики остаются основой приложения.
- Ограничения: до трёх разных товаров в одном заказе, по одной штуке;
  сотрудник из кадрового справочника со стажем не менее трёх месяцев.
- Номера новых заказов: `MERCH-00000001` и далее. Старый формат не был передан.
- Недостающая логика статусов: заказ резервирует товар; отправка или получение
  списывает его; отмена до отправки освобождает резерв; отмена отправленного
  заказа возвращает товар. Полученные/отменённые/отклонённые заказы нельзя
  открыть заново. Повторное сохранение статуса не меняет склад повторно.
- Для защиты от параллельных заказов используются блокировки остатков.
  Заказы и позиции создаются только через RPC: прямой INSERT закрыт.
  Это осознанное усиление переданных RLS-политик.
- Таблицы carts/cart_items и product_limits сохранены для совместимости;
  текущий интерфейс хранит корзину в памяти, периодические лимиты не реализованы.
- Шаблон DOCX и поля накладной присутствуют в оригинале, но интеграции печати
  накладной/доставки не восстановлены из одного шаблона. Работает существующая
  печать наклейки с QR-кодом; оплаты в исходном приложении нет.
- Старый каталог, фотографии, пользователи и история требуют отдельного экспорта.

## Изменение SQL

`supabase/base.sql` и `supabase/runtime.sql` вместе с оригинальными SQL-файлами
собираются `npm run db:build` в одну свежую миграцию. После первого применения
к облачной БД не редактируйте уже применённую миграцию для обновления сервера:
добавляйте новые версионированные миграции и проверяйте их отдельно.
