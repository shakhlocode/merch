## Как использовать read-only проверку

В корпоративной системе секретов/конфигурации:
- NEXT_PUBLIC_APP_URL и NEXT_PUBLIC_SUPABASE_URL — фактически настроенные origins;
- NEXT_PUBLIC_SUPABASE_ANON_KEY — только publishable/anon key, не service_role/secret;
- MERCH_RELEASE_ID — commit развёрнутого приложения (CI_COMMIT_SHA), возвращается сервером;
- MERCH_EXPECTED_APP_ORIGIN, MERCH_EXPECTED_SUPABASE_ORIGIN, MERCH_EXPECTED_RELEASE — утверждённые ожидаемые значения.

После применения миграций и развёртывания, до допуска пользователей: `npm run security:deployment`. Только GET, без регистрации/писем/записи данных. Единственный lookup использует вымышленный `deployment-check-nonexistent@example.invalid`; ответ RPC не выводится и не сохраняется. Ключи не выводятся, redirects при проверках запрещены, ответы неизвестного окружения не считаются успехом. Exit 1 — остановить выпуск и разобраться.

Проверка касается **основного Supabase-приложения**, не отдельного прямого PostgreSQL-прототипа. Для будущей иной архитектуры нужен соответствующий контроль. Release marker/заданный SHA полезен против случайной путаницы; это не криптографическая аттестация сборки и не замена проверке deployment commit/переменных средствами CI.

## Последовательность применения

1. Определить владельца/фактическую конфигурацию каждого Vercel/Supabase стенда. Ненужные внешние стенды закрыть и удалить по согласованной процедуре, без потери нужных данных.
2. В нужном Auth включить подтверждение почты. Для приглашений-only режима отдельно согласовать запрет самостоятельной регистрации; не отключать её вслепую, если текущий email journey её использует. Скрипт допускает регистрацию с обязательным подтверждением.
3. Проверить историю старых auto-confirm аккаунтов. Не подтверждать её безопасность только наличием email_confirmed_at. Решение об отзыве сессий/повторном подтверждении принимается владельцем и ИБ, не выполняется автоматически этим patch.
4. Применить недостающие SQL по порядку с backup/проверкой копии, обновить приложение и Auth config. Не запускать начальную миграцию на существующей БД. В обычную пустую PostgreSQL без зависимостей Supabase эта SQL отдельно не применима.
5. Выполнить read-only release check, затем на специально разрешённом синтетическом аккаунте проверить отсутствие сессии/доступа до email confirmation и появление после подтверждения. Этот тест требует создания аккаунта/письма и не выполняется автоматически против внешнего сервиса.
6. Повторить проверку ИБ итогового окружения. Корпоративные СЗИ/сетевые ограничения, журналы и Keycloak всё ещё требуют настройки: DEPLOYMENT-READINESS.md.

Нет утверждения, что найденные настройки исправлены на старом публичном сайте. Этот commit готовит код/конфигурацию/тесты и проверку выпуска, а не управляет облачной средой.
