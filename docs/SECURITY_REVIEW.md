# Передача Uzum Merch Shop на проверку

Дата подготовки: 16 октября 2026 года. Исходная версия приложения: `050908ab608ed9e0b2260162148c398a64582c27`, ветка `codex/restore-merch-system`. Этот документ описывает состояние для проверки, а не заключение о безопасности или соответствии законодательству.

## Что передано

Репозиторий содержит пользовательский интерфейс, административный интерфейс, серверные обработчики Next.js, SQL-миграции, тесты БД, зависимости с lock-файлом и документацию. Последняя миграция: `supabase/migrations/20261016002100_identifier_pvz_delivery.sql`.

Живые записи БД, учётные записи, сессии, резервные копии, содержимое Supabase Storage, секреты и настройки облачных кабинетов в репозиторий не включены. Для проверки исходного кода они не требуются. Выгрузки сотрудников и заказов не следует добавлять в Git.

Некоторые ранние инструкции описывают промежуточные версии, включая Code 128. Сейчас получение заказов использует QR-коды. Для актуальных изменений см. также BROWSER_ACCESS_RECOVERY.md, PVZ_DELIVERY.md, BUSINESS_UNITS.md, STORE-SCOPES.md и BATCH_LABELS.md в этой папке.

## Назначение и архитектура

Внутренний сервис бесплатной раздачи корпоративного мерча: доступ по реестру и приглашениям, основной каталог и Welcome pack, оформление заказов, резервирование, комплектация, выдача, ручное сопровождение отправлений, остатки и аналитика. Продажи, платежи, интеграции WMS и маркетплейсов не реализованы.

Текущий сайт: https://uzum-merch-taupe.vercel.app. Next.js/React работает на Vercel. Supabase предоставляет PostgreSQL, Auth и Storage. Браузер обращается к Next.js и Supabase Auth; сервер обращается к Supabase. Изображения товаров находятся в публичном бакете `merch-products`. QR формируются локально библиотекой, без передачи кода внешнему генератору.

Fintech, E-com и Technologies имеют отдельные каталоги, настройки и остатки. Администратор ограничен назначенным магазином, супер администратор может переключаться между магазинами и управлять ролями. Клиентский выбор магазина не должен заменять серверную авторизацию: для этого применяются RLS, SQL-функции, проверки API и связи данных внутри магазина.

## Персональные данные и выходящие копии

Обрабатываются ФИО, email, идентификатор сотрудника, телефон, кадровые атрибуты, принадлежность к реестру, права и сроки доступа. Заказы содержат выбранные товары, контакты, офис, страну/город, даты приезда, код ПВЗ, комментарии, ответственного и, для международной отправки, трек-номер. Auth хранит сведения для аутентификации и сессий; журналы содержат действия и их авторов.

CSV, скачанные изображения QR, печатные этикетки и сохранённые PDF образуют отдельные копии данных на устройствах. Их хранение, пересылку и уничтожение необходимо включить в корпоративные правила. Публичный бакет предназначен только для фотографий товаров, не для документов и персональных данных.

Регион размещения, трансграничную передачу, договоры с провайдерами, сроки хранения, резервное копирование, удаление данных, MFA облачных администраторов и доступ технических специалистов следует отдельно проверить в кабинетах и корпоративных документах. Исходный код не подтверждает выполнение этих требований.

## Вход, приглашения и получение

- Вход через email использует Supabase Auth. Сам факт регистрации не предоставляет доступ к каталогу: требуется разрешение реестра/приглашения.
- Для пользователей без почты есть персональная ссылка и идентификатор. Активация однократная, доступ закрепляется за аккаунтом; дальнейший вход зависит от сохранённой браузерной сессии. Это не аппаратная привязка устройства и не защита от добровольной передачи доступа до активации или копирования сессии.
- Администратор может восстановить браузерный доступ после проверки личности вне системы. Восстановление сохраняет аккаунт и историю, отзывает прежний браузерный доступ и не должно обнулять использованное право заказа.
- Welcome pack открывается по соответствующему приглашению и выдаётся очно в выбранном офисе. Основной каталог имеет отдельный доступ.
- При оформлении резервируется товар. Очная выдача по случайному 20-значному коду в QR разрешена подготовленному заказу. Код не содержит ФИО или телефона, но является секретом предъявителя: скриншот можно передать другому человеку.
- Статус, списание, автор выдачи и событие сохраняются одной транзакцией. Повторное сканирование не должно повторять списание. QR не подтверждает личность предъявителя — при необходимости нужна проверка сотрудника на выдаче.
- Международная отправка и доставка в свой ПВЗ сопровождаются вручную, без сканирования QR. ПВЗ доступен только соответствующим пользователям, активировавшим вход по идентификатору. Интеграции с перевозчиком и проверки существования ПВЗ нет.

## Переменные и секреты

Шаблон имён — `.env.example`:

| Имя | Назначение |
| --- | --- |
| NEXT_PUBLIC_SUPABASE_URL | Публичный адрес проекта |
| NEXT_PUBLIC_SUPABASE_ANON_KEY | Публичный клиентский ключ; защита зависит от RLS и авторизации |
| NEXT_PUBLIC_APP_URL | Адрес приложения и переходов |
| SUPABASE_SERVICE_ROLE_KEY | Только сервер; привилегированный ключ, обходящий RLS |
| INVITE_EMAIL_ENABLED | Разрешение отправки приглашений после настройки SMTP |

`SUPABASE_ACCESS_TOKEN` и `VERCEL_TOKEN` используются для управления инфраструктурой, не должны попадать в клиентский bundle или Git. SMTP настраивается отдельно в Supabase Auth; пароль не хранится в исходниках. По последней проверке среды отправка административных приглашений отключена (`INVITE_EMAIL_ENABLED=false`); настройку писем регистрации и восстановления Auth необходимо проверять отдельно.

В миграциях есть начальное назначение владельца по конкретному email. Перед независимой установкой нужно проверить, кому будут выданы первоначальные полномочия. Не использовать производственные ключи и почтовые настройки в тестовой копии.

## Точки проверки в исходниках

- `app/api/` — серверная авторизация, валидация, приглашения, восстановление, экспорт и операции с заказами.
- `lib/`, `proxy.ts` — контекст магазина, Supabase-клиенты, сессии, QR и вспомогательная логика.
- `supabase/migrations/` — RLS, ограничения, права функций, резервирование, выдача, доступ между магазинами.
- `scripts/` — сборка схемы и проверки БД.
- `app/admin/`, `app/orders/`, `components/` — отображение персональных данных, QR, экспорт, печать и сообщения.

Особое внимание: вызовы с service-role, функции SECURITY DEFINER и их search_path/GRANT, роль `merch_executor`, прямые запросы к REST/RPC в обход интерфейса, подмена магазина и ID объектов, отзыв доступа и конкурентные операции с остатками.

## Известные вопросы, которые не исправлялись при передаче

1. Приглашения устанавливают признак одного заказа независимо от выбора бессрочного/срочного доступа. Доступ без такого приглашения может допускать несколько заказов. Требуется согласовать единую политику.
2. Использование одноразового доступа закрывает также пользовательскую историю и профиль. Истечение срока/деактивация могут закрыть просмотр QR при ещё не завершённом заказе и сохранённом резерве. Нужно отдельно определить права на уже созданные заказы после отзыва доступа.
3. `admin_comment` показывается сотруднику. Его нельзя считать внутренней закрытой заметкой.
4. Деактивация в HR-реестре не равнозначна отзыву административной роли. При увольнении нужны обе операции.
5. В списках заказов, сотрудников и товаров нет полноценной постраничной загрузки. При больших объёмах стандартный лимит Supabase может ограничить поиск, экспорт и печать видимой выборкой. Это риск полноты данных, требующий нагрузочной проверки.
6. Режим ПВЗ ещё не добавлен в фильтры/подписи аналитики: в общей выборке такие выдачи могут подписываться как офисные.
7. Напоминания о приезде работают в открытом интерфейсе администратора, без гарантированной фоновой рассылки. Резерв не снимается автоматически после даты отъезда; сообщение о двух неделях для ПВЗ — текст, не автоматический контроль доставки.
8. Отмена отправленного заказа возвращает остаток в системе: администратор должен подтвердить фактический возврат товара. Отдельного процесса исправления ошибочной выдачи/возврата полученного заказа нет.
9. Редактируемые правила не меняют программные ограничения: максимум три разных товара, по одной штуке. Нет отдельной сущности кампании раздачи; изменение текстов влияет и на сообщения старых заказов.
10. Ссылка «В магазин» сохраняет права администратора и не является имитацией обычного пользователя. Для проверки разграничения нужны отдельные тестовые аккаунты.

## Проверки и ограничения доказательств

До подготовки этой передачи выполнялись сборка, lint, SQL-проверки, конкурентные сценарии списания/выдачи, сценарии восстановления входа и браузерные проверки QR. Это сведения о предыдущих проверках, не новый независимый аудит. Работу камер и сканеров необходимо дополнительно проверить на реальных устройствах.

При подготовке передачи проверены 733 файловых объекта доступной Git-истории: совпадений с доступными локальными секретами и выбранными шаблонами токенов/закрытых ключей не найдено. В Git отслеживается только `.env.example`, не `.env.local`. Эта ограниченная проверка не исключает секреты неизвестного формата и не заменяет специализированный сканер, анализ зависимостей и пентест.

Для независимой проверки рекомендуется отдельный Supabase-проект с синтетическими сотрудниками, отдельными ключами и тестовой почтой. Порядок установки описан в SETUP.md; миграции применяются последовательно к новой базе. Не запускать повторную инициализацию на рабочей БД. Для проверок доступны `npm ci`, `npm run build`, `npm run lint`, `npm run db:test` (для последней команды нужен Docker).
