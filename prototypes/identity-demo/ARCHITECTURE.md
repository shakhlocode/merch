# Схема, данные и права для предварительной проверки

## 1. Компоненты и изоляция

Все данные синтетические. Compose создаёт сеть `internal: true`: контейнеры общаются друг с другом и не имеют обычного внешнего маршрута. Docker-порты не публикуются. Локальный Node.js-мост `scripts/ports.mjs` слушает только loopback и передаёт TCP через `docker exec` к приложению и тестовому Keycloak. PostgreSQL наружу не опубликован. Образы и npm-пакеты скачиваются при подготовке, а не при работе интеграции. Используемые версии зафиксированы тегами и npm lock-файлом; анализ уязвимостей образов — отдельная проверка, не свойство их фиксации.

Секреты генерируются при первом запуске. `.local/`, зависимости и артефакты игнорируются Git; `.local/` также исключена из Docker build context. Приложение получает только собственные demo-переменные, не наследует `.env.local` основного проекта. Оно явно отклоняет недемонстрационные origins/client ID. Рабочие домены, ключи Supabase, SMTP и корпоративные API кодом стенда не используются.

Приложение работает непривилегированным пользователем ОС, с read-only filesystem и без Linux capabilities. Его PostgreSQL-роль не superuser, без CREATEDB/CREATEROLE/BYPASSRLS. Для упрощения автономной установки эта роль владеет тестовой БД и создаёт demo-таблицы. В production роли мигратора и приложения следует разделить.

## 2. Корпоративный вход

```mermaid
sequenceDiagram
    actor U as Сотрудник (тест)
    participant B as Браузер
    participant A as Сервер мерчшопа
    participant K as Тестовый Keycloak
    participant D as Тестовая PostgreSQL
    U->>B: Войти корпоративным аккаунтом
    B->>A: GET /auth/login
    A->>D: state hash, PKCE verifier, nonce (5 минут)
    A-->>B: Redirect + HttpOnly flow cookie
    B->>K: authorization request (openid profile email, PKCE)
    U->>K: Тестовые учётные данные или существующая SSO-сессия
    K-->>B: Redirect с одноразовым code и state
    B->>A: GET /auth/callback
    A->>D: Проверить и однократно потребить flow
    A->>K: code + verifier + server client authentication
    K-->>A: ID/access/refresh tokens
    A->>K: JWKS для проверки подписи
    Note over A: Проверить iss, aud/azp, exp, iat, nonce, email_verified
    A->>D: Найти заранее связанную личность; проверить реестр
    A->>D: Обновить кадровые поля, создать локальную сессию
    Note over A: Токены провайдера не сохранять
    A-->>B: HttpOnly cookie собственной сессии; redirect в магазин
```

Браузер не передаёт пароль Keycloak серверу мерчшопа. Токены от token endpoint остаются на сервере и не попадают в HTML/API/журнал. Refresh token не используется. Scopes `offline_access`, административные scopes и доступ ко всем пользователям не запрашиваются.

### Контракт данных

| Поле | Источник | Использование |
| --- | --- | --- |
| iss + sub | Подписанный ID token | Стабильная привязка личности к локальному аккаунту |
| email + email_verified | Подписанный ID token | Отображение подтверждённой почты, обновление профиля; не автоматическое слияние аккаунтов |
| name | Подписанный ID token | ФИО в профиле и снимке заказа |
| employee_id | Дополнительный mapper тестового клиента | Проверка соответствия заранее созданному реестру |
| legal_entity | Дополнительный mapper | Юрлицо в профиле и снимке заказа |
| department | Дополнительный mapper | Отдел в профиле и снимке заказа |
| unit, scope, active, access_used | Только локальный реестр | Разрешение на магазин/раздел/заказ |
| sid | Подписанный ID token | Привязка локальной сессии к событию back-channel logout |

Сотрудник не может редактировать кадровые поля в checkout. Сервер отклоняет попытку передать их, `unit`, `scope`, `role` или чужой ID. Для нового заказа кадровый снимок читается из БД в транзакции, а не из браузера. Изменение email не меняет `iss + sub`, локальный user ID и уже сохранённые снимки заказов.

Дополнительные mappers должны в реальном Keycloak брать значения из доверенного источника, а не из доступных сотруднику для редактирования полей. В демонстрации все они заданы в синтетическом realm; доступ к самообслуживанию через мерчшоп отсутствует. На настоящий HR API приложение не обращается.

## 3. Вход по идентификатору

```mermaid
sequenceDiagram
    participant B as Браузер
    participant A as Сервер мерчшопа
    participant D as Тестовая PostgreSQL
    Note over B: Персональная ссылка из локального тестового ящика
    B->>A: Открыть форму /guest (токен в fragment)
    A-->>B: Форма + отдельная CSRF cookie
    B->>A: POST token + identifier + CSRF
    A->>D: Блокировка приглашения, проверка hash, срока и попыток
    A->>D: Проверить активность реестра
    A->>D: Создать аккаунт; пометить приглашение использованным; создать сессию
    A-->>B: HttpOnly session cookie
    B->>A: Повторное посещение с cookie
    A->>D: Проверить сессию и актуальное разрешение
    A-->>B: Свой магазин без повторной активации
```

В БД хранится hash случайного токена приглашения и hash идентификатора с солью-ID приглашения. Приглашение живёт 7 дней; максимум 8 неверных попыток. Проверка и активация транзакционны, два параллельных запроса не создают два аккаунта. Сессии хранятся в БД в виде HMAC токенов; исходный токен — только в HttpOnly cookie. Это привязка к сессии браузера, не к аппаратному идентификатору устройства. Дубликаты cookie и добровольную передачу приглашения до активации такая схема не исключает.

## 4. Заказ и данные получения

| Поле | Кто вводит | Когда сохраняется |
| --- | --- | --- |
| Товары, цвет, размер | Сотрудник | При создании тестового заказа |
| Телефон | Сотрудник | При создании заказа, обязательный контакт для получения |
| Офис | Выбор из тестового списка | Для очной выдачи |
| Страна, город, адрес | Сотрудник | Только для отправки |
| Код ПВЗ | Сотрудник по идентификатору | Только для получения в своём ПВЗ |
| Комментарий | Сотрудник | Только для доставки/ПВЗ |
| ФИО, email, юрлицо, отдел | Сервер из доверенной записи | Снимок на момент заказа |

Welcome pack разрешает только офис. Сервер фильтрует историю по аккаунту, магазину и разделу. Браузер не может выбрать себе другой магазин или роль. Полный учёт остатков, лимит до получения одного заказа и выдача остаются в рабочей системе и здесь не воспроизводятся.

## 5. Сессии, выход и отзыв

- Сессия мерчшопа: 15 минут, без silent refresh. Cookie HttpOnly/SameSite=Lax; локальный HTTP без Secure строго ограничен конфигурацией и loopback-портами.
- Все изменяющие браузерные запросы проверяют Origin; создание заказа и logout дополнительно проверяют CSRF-токен. OIDC callback привязан к flow cookie + state + nonce + PKCE, повторный flow отклоняется.
- Logout в мерчшопе удаляет серверную сессию; восстановленная старая cookie больше не работает. Общая SSO-сессия Keycloak остаётся, это явно указано в интерфейсе.
- `/auth/backchannel-logout` принимает только подписанные JWT тестового issuer для нашего audience, проверяет время, event, отсутствие nonce, jti и sid/sub. jti сохраняется для защиты от повтора. Корпоративные сессии удаляются, гостевые не затрагиваются.
- Отключение сотрудника в локальном реестре закрывает защищённые запросы. Отдельно требуется согласовать, как события увольнения попадают из корпоративной системы в этот реестр.
- Блокировка учётной записи Keycloak препятствует новому входу, но не является гарантией доставки logout для старых сессий. Немедленный отзыв требует реальной политики, механизма уведомлений и проверки отказов.

## 6. Что хранится и чего не запрашиваем

В demo-БД: синтетические кадровые поля, привязка `iss + sub`, разрешения, hashes приглашений/сессий, временные OIDC flows, снимки тестовых заказов, безопасные описания событий, replay IDs logout. Временный PKCE verifier удаляется при callback; истёкшие flows очищаются при новом начале входа.

Не запрашиваем пароль сотрудника, список всех пользователей Keycloak, административные права провайдера, доступ к другим корпоративным приложениям, паспортные данные или аппаратный ID устройства. Локальные секреты приложения и тестовые пароли не входят в Git. Политика хранения/удаления, централизованный аудит и резервное копирование production согласуются отдельно; у демо данные полностью сбрасываются удалением его volumes.
