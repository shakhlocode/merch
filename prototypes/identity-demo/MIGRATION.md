# Что потребуется для реальной интеграции

Эта демонстрация не переключает авторизацию рабочего приложения. Она показывает отдельный, проверяемый путь прямого OIDC и серверных сессий. Перед переносом нужно согласовать архитектуру и выполнить отдельную реализацию.

## Зависимости действующего проекта

| Текущее место | Зависимость | Дальнейшее действие |
| --- | --- | --- |
| `app/login/page.tsx` | Supabase email OTP/password | Корпоративный OIDC вместо отдельного пароля; не оставлять email-вход как обход обязательного SSO |
| `app/auth/callback/route.ts`, `app/auth/hash-callback/page.tsx`, `app/set-password/` | Supabase session + password_set_at | Callback OIDC, собственная сессия, пропуск установки локального пароля для корпоративных аккаунтов |
| `lib/supabase/server.ts`, API/SSR pages | getUser(), Supabase cookie/JWT | Единый серверный auth context для OIDC и идентификаторного входа |
| `app/api/invitations/redeem/route.ts` | Технические Supabase Auth users для гостей | Собственные локальные пользователи; сохранить одноразовую активацию и восстановление без потери истории |
| `app/api/invitations/accept/route.ts`, `lib/invitations.ts` | Почтовый вход Supabase | SMTP доставляет приглашение; корпоративную личность подтверждает Keycloak |
| SQL RLS/RPC, `auth.uid()`, `auth.sessions` | Идентичность Supabase | Проектировать новый безопасный контекст БД; не отключать проверки без замены |
| `shop_admins`, `shop_super_admins`, сопоставление реестра | Email в правилах ролей | Мигрировать привязки к локальному user ID / стабильной корпоративной личности, проверив владельцев |
| Storage, PostgREST и SDK | Supabase-платформа вне Auth | Выбрать внутренние сервисы и защищённый серверный доступ; Keycloak их не заменяет |

## Предлагаемый порядок

1. Утвердить схему прямого OIDC, поля, доверенные mappers, минимальные scopes и правила отзыва.
2. Решить, где хранить фото и как сервер обращается к PostgreSQL. Разделить роль мигратора и рабочую роль, сохранить межмагазинную изоляцию и атомарность склада.
3. На изолированной копии данных внедрить единые локальные аккаунты и серверные сессии. Не переносить production cookies или пароли в демонстрационный стенд.
4. Сопоставить существующие аккаунты с корпоративными идентичностями под контролем администратора; не сливать автоматически по неподтверждённому email. Сохранить UUID пользователей либо явно и транзакционно перенести связи заказов, ролей и доступа.
5. Реализовать весь гостевой путь, восстановление, закрытие доступа после выдачи и доступ к уже созданным заказам. Известные конфликты одноразового доступа из SECURITY_REVIEW.md должны быть разрешены отдельно.
6. Настроить серверный SMTP и безопасную очередь приглашений. Нужны retries, лимиты, срок действия и проверка адресата. Приглашение не должно обходить корпоративный вход.
7. Проверить OIDC security failures, смену email, отзыв/истечение сессий, изоляцию магазинов, роли, конкурентное резервирование, повторное сканирование и экспорт на тестовой среде.
8. После разрешения подключить корпоративный тестовый клиент, подтвердить совместимость с реальными настройками Keycloak, затем планировать production-миграцию с резервной копией и откатом.

## Что нужно подтвердить у команды портала

- Realm/discovery URL; отдельные тестовый и рабочий confidential clients, Code Flow + PKCE S256, exact redirect URIs.
- Гарантии стабильности `iss + sub`; кадровый идентификатор и процедура смены email/повторного найма.
- Claims `email_verified`, ФИО, юрлицо, отдел: доверенный источник и запрет самостоятельной подмены. Если поля недоступны — отдельная спецификация HR API с минимальными правами.
- Политики MFA, срока сессии, локального/общего logout, поддержка back-channel logout и поведение при отключении пользователя.
- Механизм статуса сотрудника, гарантия/повторы уведомлений, требуемое время отзыва и действия при недоступности провайдера.
- Сетевая доступность с сервера и с личных телефонов вне офиса, TLS/CA и тестовые аккаунты.

## Перед рабочим размещением

Перейти с локального HTTP на HTTPS, Secure cookies, реальные утверждённые origins и защищённое хранилище секретов. Не снимать ограничения demo-конфига и не превращать данный стенд в production заменой URL: это отдельная реализация с недостающими бизнес-функциями, эксплуатационными требованиями и проверками.
