# Изолированный прототип корпоративного входа

Стенд для предварительной проверки архитектуры, **не новая версия рабочего мерчшопа**. Дата: 23 октября 2026 года.

Вместо корпоративного Keycloak используется отдельный настоящий Keycloak с вымышленными аккаунтами. Это позволяет проверить реальный OIDC Authorization Code Flow + PKCE, а не просто переключить пользователя по кнопке. Корпоративные системы, действующая БД, SMTP и Supabase Auth не используются.

## Что можно показать

1. Корпоративный вход без создания пароля мерчшопа.
2. ФИО, email, юрлицо и отдел, полученные от тестового провайдера, без редактирования.
3. Доступ к каталогу E-com или Welcome pack Fintech строго по локальному реестру, а не по кадровому БЮ или ролям Keycloak.
4. Отказ пользователю без разрешения реестра и заблокированному аккаунту.
5. Сохранение локального ID и истории при корпоративном входе и смене email.
6. Отдельный вход по персональной ссылке и идентификатору: одна активация, сохранённая браузерная сессия.
7. Телефон и способ получения, а при отправке — страна, город и адрес. Кадровые сведения берутся сервером из доверенных данных и сохраняются в снимке тестового заказа.
8. Локальный выход и отзыв корпоративных сессий через подписанный back-channel logout Keycloak.
9. Страницу «Схема для проверки» с обезличенным журналом взаимодействий.

## Запуск на отдельной машине

Нужны Node.js 24, npm, Docker Engine и Compose v2. Ориентир для этого небольшого стенда — 4 ГБ свободной RAM и несколько ГБ диска. Это не sizing рабочей системы.

Из корня репозитория:

```bash
cd prototypes/identity-demo
npm ci
npm run init
docker compose --env-file .local/demo.env up -d --build
```

Во втором терминале в той же папке запустить локальный мост и оставить его работающим:

```bash
npm run ports
```

Мост слушает только `127.0.0.1` и передаёт TCP через `docker exec` в закрытую сеть. Контейнерам не нужен внешний сетевой интерфейс или опубликованные Docker-порты. Для запуска моста нужен доступ к локальному Docker Engine.

Первый запуск Keycloak может занять минуту. Проверка готовности:

```bash
curl --fail http://127.0.0.1:3180/health
```

Открыть стенд в браузере на этой же машине: адрес `127.0.0.1`, порт `3180`. Тестовый Keycloak использует порт `8180`. Для показа в этой облачной среде не предполагается публичный preview: используйте скриншоты ниже или запустите пакет на выделенном компьютере. Ничего не публиковать на рабочем домене.

Пароль всех вымышленных корпоративных пользователей сгенерирован при `npm run init` и записан в **`.local/accounts.json`**. В Git пароль не хранится. Пользователи:

| Логин | Сценарий |
| --- | --- |
| alice | Каталог E-com, существующий локальный аккаунт и тестовый старый заказ |
| boris | Welcome pack Fintech, только офисная выдача |
| outsider | Вход в Keycloak успешен, но разрешения реестра нет |
| blocked | Аккаунт отключён в тестовом Keycloak |

Для второго способа входа откройте «Тестовый ящик приглашений» на главной странице. Там вымышленное приглашение и идентификатор `TEST-GUEST-001`. Оно активируется только один раз. Тестовый ящик заменяет email/мессенджер: никакие сообщения не отправляются. Общедоступность ящика допустима только в этом локальном демо и **не является предлагаемой политикой рабочего приложения**.

В браузере не используйте `localhost` вместо `127.0.0.1`: origins/callback зафиксированы для защиты от случайного подключения другой среды. Для сетевого показа коллегам понадобится отдельно согласованная конфигурация доменов и HTTPS, а не публикация этих локальных портов.

### Сборка за корпоративным HTTPS-прокси

Если Docker не доверяет сертификату прокси, подключите утверждённый CA как временный build secret. Не отключайте TLS-проверку:

```bash
docker build --secret id=build_ca,src=/путь/к/доверенному-ca.crt -t merch-identity-demo-app .
docker compose --env-file .local/demo.env up -d --no-build
```

CA не копируется в итоговый образ. Для обычного запуска этот шаг не нужен.

### Остановка и повторный показ

```bash
docker compose --env-file .local/demo.env stop
docker compose --env-file .local/demo.env up -d --no-build
```

Повторный запуск сохраняет вымышленные заказы и использованные приглашения. Для **полного сброса только этого демо**, включая возможность заново активировать приглашение:

```bash
docker compose --env-file .local/demo.env down --volumes
docker compose --env-file .local/demo.env up -d --no-build
```

Команда удаляет только volumes Compose-проекта `merch-identity-demo`. Не менять имя проекта на рабочее. Секреты в `.local/` сохраняются. Для их замены сначала остановить/сбросить демо, затем удалить именно локальную папку этого прототипа и повторить инициализацию. Не использовать секреты от рабочей системы.

## Проверки

```bash
npm test
```

Браузерные проверки требуют **свежей тестовой БД**, потому что намеренно используют одноразовое приглашение:

```bash
npx playwright install chromium
npm run test:e2e
```

Если браузер уже установлен в ОС, вместо скачивания можно указать путь:

```bash
DEMO_CHROMIUM=/usr/bin/chromium npm run test:e2e
```

Проверки работают только с локальным стендом, без production-секретов. Они меняют email вымышленной alice через локальный Keycloak Admin API и возвращают его обратно, проверяют logout, создают вымышленные заказы и активируют тестовое приглашение. Доступ к Admin API нужен **только тестовому runner**, не приложению мерчшопа. Скриншоты сохраняются в игнорируемую папку `artifacts/`.

## Состав

- `compose.yaml` — три отдельных контейнера: приложение, PostgreSQL, тестовый Keycloak.
- `scripts/init.mjs` — создаёт синтетический realm, пользователей и случайные локальные секреты.
- `server.mjs` — собственные сессии, прямой OIDC, приглашения и минимальная форма тестового заказа.
- `security.mjs` — проверки конфигурации, claims и данных заказа.
- `schema.sql` — отдельные `demo_*` таблицы; рабочие миграции не запускаются.
- [ARCHITECTURE.md](ARCHITECTURE.md) — взаимодействия, данные, права и границы доверия.
- [MIGRATION.md](MIGRATION.md) — что потребуется изменить в рабочем проекте после согласования.
- [SHOWCASE.md](SHOWCASE.md) — скриншоты и последовательность демонстрации без запуска Docker.
- [VALIDATION.md](VALIDATION.md) — выполненные проверки и их границы.

## Ограничения

- Это автономный прототип входа и проверки прав. Полный рабочий интерфейс, склад, списание, QR, реальный импорт, восстановление гостевого входа и отправка SMTP здесь не дублируются.
- Все локальные сессии живут 15 минут без автоматического продления. Они не привязаны к аппаратному ID телефона.
- Нет автоматического слияния аккаунтов по email. Синтетические сотрудники заранее связаны с `iss + sub`; процедура миграции настоящих пользователей требует отдельной проверки.
- Смена email не переносит права на другой аккаунт. Роли Keycloak не назначают роли мерчшопа.
- Back-channel logout реализован. Простая блокировка аккаунта Keycloak без события logout **не гарантирует немедленного отзыва существующей локальной сессии**. Для рабочего решения нужен согласованный механизм статуса/отзыва и SLA.
- Параметр `active` локального реестра проверяется при каждом защищённом запросе. Для корпоративных кадровых данных показано обновление при входе, не постоянная синхронизация HR.
- Нет тестового API HR: в выбранном демонстрационном контракте кадровые поля приходят подписанными claims Keycloak. Если в компании так невозможно, добавление HR API будет отдельной согласуемой интеграцией.
- Не предусмотрены производственный HTTPS, HA, централизованный мониторинг, долговременное хранение и регламент удаления. HTTP и cookies без Secure допустимы здесь только из-за строго локального режима; для рабочего размещения обязателен HTTPS и Secure cookies.
- Стенд не является одобрением ИБ и не доказывает совместимость с настройками корпоративного Keycloak без отдельной интеграционной проверки.
