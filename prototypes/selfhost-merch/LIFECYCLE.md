# Корпоративные данные, HR и удаление: контракт мокового стенда

29 октября 2026. Реализовано только в отдельном серверном стенде с вымышленными данными. Рабочий Vercel/Supabase не переключены. Корпоративная PostgreSQL ещё не предоставлена. Новый стенд использует PostgreSQL напрямую, без Supabase Auth.

## Данные и доступ с портала

OIDC Authorization Code + PKCE через отдельный тестовый Keycloak. Из доверенных claims: `sub`, `name`, подтверждённая `email`, `business_unit`, `legal_entity_name`, код `legal_entity_code`, группы мерча `merch_groups`, `employee_active`, необязательное `delete_at` (ISO timestamp с часовым поясом либо отсутствует).

ФИО, корпоративная почта, кадровые БЮ/юрлицо и дата удаления сохраняются в минимальном профиле. Кадровое БЮ не определяет магазин автоматически. Магазин и раздел определяет разрешение администратора по человеку/юрлицу/группе. Участник создаётся при первом разрешённом входе: отдельный HR-файл офисных сотрудников не нужен. Источник поиска людей пока синтетический адаптер, настоящий API не подключён.

`delete_at` — согласуемый пользовательский атрибут, не стандартная возможность OIDC. Его отсутствие не означает известную дату увольнения. Временная сессия 15 минут не решает синхронизацию удаления для человека, который больше не входит.

## Удаление независимо от входа

Контракт `POST /api/lifecycle/events`: JSON с `id` UUID, `kind` (`updated`, `scheduled`, `deleted`, `terminated`), `subject` из настроенного источника. Для обновления: `full_name`, `email`, `business_unit`, `legal_entity`, `deletion_at`. Для события HR предусмотрен необязательный путь `source: "hr"` + `pinfl`, но по текущему решению пользователя такого автоматического HR-источника **нет**.

Событие подписывается отдельным ключом `DEMO_LIFECYCLE_KEY`:

- `x-event-timestamp`: Unix milliseconds, окно 5 минут;
- `x-event-signature`: hex HMAC-SHA256 от `timestamp + "\n" + JSON.stringify(body)`;
- повтор того же event ID с тем же телом безопасен; конфликт тела отклоняется;
- тело с ПД не пишется в аудит; для replay хранится только ID и HMAC тела, 10 минут.

Порядок ключей JSON в подписи должен совпадать. До настоящего подключения требуется согласовать канонизацию, ключи/ротацию, HTTPS/mTLS, формат, последовательность кадровых изменений, доставку с retry и сверку после сбоев. Старое событие обновления не должно отменять новое кадровое решение: полноценное версионирование источника/периодическая сверка — задача реальной интеграции. Уже удалённая личность автоматически не восстанавливается событием обновления.

Полученное событие удаления синхронно вызывает отдельный процесс удаления; успешный ответ даётся после применения. Если источник неизвестен локально, записывается блокирующая техническая метка — будущий вход не создаст удалённого человека заново. Запланированное удаление выполняется worker независимо от браузера с периодом 5 секунд; API закрывает доступ по наступившему сроку ещё до следующей очистки.

В админке «Кадровые события (мок)» можно задать дату или смоделировать увольнение. Это тест источника, **не установленный plugin настоящего Keycloak**. Удаление пользователя в реальном портале само по себе пока не вызовет этот API. Команда портала должна подключить авторитетные кадровые события через portal backend, Keycloak Event Listener или другой согласованный механизм и прекратить вход удалённого аккаунта в самом провайдере. Keycloak logout отзывает сессии, но сам по себе не удаляет профиль приложения.

## Массовый персонал

CSV UTF-8 с точным заголовком:

`full_name;legal_entity;position;phone;pinfl`

До 2000 строк, файл до 1 МБ. Excel можно экспортировать в CSV с разделителем `;`; чтение XLSX в этот новый стенд не перенесено. ФИО, юрлицо, должность, телефон сохраняются. ПИНФЛ передаётся в файле/при активации и существует в памяти обработки, но в БД остаются только HMAC с серверным ключом. В ссылку, письмо или журнал ПИНФЛ не включается. Предусмотрены атомарный импорт, проверка формата 14 цифр, сохранение ведущих нулей, защита дубликатов и привязка к одному магазину.

Организатор получает персональную случайную ссылку для каждого человека в тестовом ящике и передаёт её лично. Активация требует ссылку + совпадающий ПИНФЛ. Знания только ПИНФЛ недостаточно. Это сверка с HR-реестром, не доказательство личности и не гарантия от добровольной передачи ссылки и кода.

После активации — HttpOnly браузерная cookie и серверная сессия на 30 дней. Повторное открытие в том же профиле браузера не требует активации. Смена телефона, очистка cookie, истечение срока — восстановление через администратора, с сохранением аккаунта/заказа и отзывом старой сессии. Аппаратный ID устройства не собирается. После выдачи/отправки сессии удаляются и доступ закрывается.

Автоматически узнавать увольнение массового персонала неоткуда: по решению пользователя для него действует удаление через два месяца после выдачи/отправки. Пропуск человека в следующем файле не означает увольнение. Для отдельного запроса есть ручное удаление; канал кадровых событий HR технически подготовлен, но не подключён.

## Два месяца и сохранность склада

При `received` или `shipped` статус, складское движение, прекращение доступа, `fulfilled_at` и `purge_after` фиксируются вместе. Два **календарных** месяца рассчитываются по Asia/Tashkent, не как 60 суток. Для отправки служит отдельный выбор; после сборки администратор нажимает «Отправили доставкой», QR не выдаётся. Это фиксация отправки, не интеграция перевозчика и не доказательство вручения.

По истечении срока удаляются профиль, связи аккаунта, сессии, приглашения, письма, персональные заказы, позиции и индивидуальные движения/аудит. Незавершённый резерв освобождается при увольнении. Сохраняются товары, размеры/цвета/количества, изображения и суммарные количества выданного/отправленного без получателей. Агрегаты малых групп требуют оценки на косвенную идентификацию.

Для не завершивших заказ используется отдельная предложенная политика: два месяца после закрытия раздачи. Она не заменяет срок от выдачи и требует утверждения, поскольку пользователь определил срок только для получивших/отправленных. Прикладные события хранятся до 30 дней либо удаляются раньше вместе с участником. Служебный аккаунт администратора удаляется при соответствующем событии источника, а не по чужой выдаче.

## Изображения и товары

В PostgreSQL — тип товара, размещение, варианты размеров/цветов, остатки и резерв. Загруженные PNG/JPEG/WebP до 2 МБ хранятся в `bytea` с MIME. Изображения выдаются авторизованным серверным API с проверкой магазина/раздела. Произвольный SVG от администратора не принимается; старые SVG-заглушки стенда сгенерированы сервером и также скопированы в БД. Старый файловый volume сохранён для совместимости и backup-скриптов, но загрузки этого нового интерфейса пишут изображения в БД.

## Backup и пределы обещания «удалить всё»

Независимый журнал хранит UUID удалённых записей/раздач и HMAC метки источника, чтобы восстановление старой БД не вернуло сотрудников или доступ. ФИО/email/телефона/ПИНФЛ в журнале нет, но метки могут связываться с человеком и **не являются гарантированно анонимными**. Их жизненный цикл нужно согласовать с ИБ/DPO отдельно; в моках автоматическое уничтожение этих защитных меток не настроено.

Старые зашифрованные копии сохраняют содержимое до удаления самих архивов. Демо-ротация старше 7 дней запускается только командой backup, расписания нет. При restore журнал повторно применяется до открытия API, сессии и ссылки отзываются, раздачи остаются закрытыми для сверки физических операций после точки копии. Без доверенного журнала — карантин. Копии Keycloak, ОС/ingress/SMTP-логи, HR-файлы у HR/на компьютере, выгрузки и распечатки не удаляются SQL-очисткой приложения.

Поэтому реализовано удаление операционных персональных записей и защита от их восстановления, а не обещание мгновенно уничтожить все копии и технические метки на всех носителях. Корпоративные хранилища, ключи и политики резервных копий ещё не предоставлены.
