# Серверный стенд: собственная БД, выдача и очистка данных

Обновлено: 29 октября 2026. Отдельный работающий прототип на синтетических данных. **Рабочий сайт, его БД и оба ранее созданных демо не переключаются.** Это не завершённый перенос всех функций приложения и не разрешение на обработку реальных сотрудников.

Здесь нет облачного Supabase, Vercel, 1С, настоящего SMTP или корпоративного Keycloak. Своя PostgreSQL, серверные сессии и реальный OIDC-протокол с отдельным тестовым Keycloak. Браузер не имеет прямого доступа к БД.

## Что реализовано

- Разрешения на конкретную раздачу/магазин: E-com, Fintech, Technologies; отдельный Welcome pack.
- Прямой вход через тестовый Keycloak, доверенные claims, собственные HttpOnly сессии, back-channel logout.
- «Доступ через портал»: разрешение по юрлицу, группе или отдельному человеку из мокового каталога; исключения, выключение правил, разделение каталог/Welcome pack. Новый участник создаётся при первом разрешённом входе без предварительной загрузки HR-реестра.
- Персональное приглашение + идентификатор, одна активация, восстановление того же аккаунта с отзывом старых сессий.
- Новички без портала: личная почта, одноразовые ссылки входа, повторный вход в тот же аккаунт и автоматическое закрытие доступа при выдаче Welcome pack.
- Служебные роли организатора и администратора одного магазина, задаваемые локально, не из claims Keycloak.
- Варианты размеров, остатки, резерв, отключение товара, порог предупреждения.
- Один действующий заказ на участника раздачи, до трёх разных товаров по одной штуке. Идемпотентный повтор оформления.
- Заявка → Сборка → Можно забирать → Получен. QR содержит только случайный код. Выдача, складское движение, исполнитель и событие аудита сохраняются транзакционно; повторная выдача не списывает второй раз.
- Отмена до получения освобождает резерв. После получения история остаётся доступна до закрытия раздачи, новый заказ не разрешается.
- CSV количественной аналитики без ФИО и контактов.
- Тестовый почтовый ящик, отдельное файловое хранилище, автоматическая очистка и зашифрованная резервная копия с проверенным восстановлением.

Пилот намеренно **только очный**, без телефона, адресов, свободного комментария, отдела и даты найма. Код юрлица и группы нужны только для проверки права входа и временно сохраняются в серверной сессии, в заказ не копируются. API отклоняет попытку передать эти поля. В заказ не копируется ФИО/email: данные получателя отображаются через временную связь с профилем.

## Запуск

Нужны Node.js 24, npm, Docker Engine и Compose v2. Использовать существующий checkout, не создавать worktree без отдельной просьбы.

```bash
cd prototypes/selfhost-merch
npm ci --ignore-scripts
npm run init
chmod 644 scripts/init-db.sh
docker compose --env-file .local/demo.env up -d --build
```

Во втором терминале из той же папки:

```bash
npm run ports
```

Мост слушает только loopback: приложение — порт **3280**, тестовый Keycloak — **8280** на `127.0.0.1`. Он использует `docker exec`, чтобы не открывать контейнерам выход в интернет. Docker-порты БД/админки не публикуются; сеть `internal: true`. Для моста нужен доступ к локальному Docker. При пересоздании контейнера app мост следует перезапустить.

В этой облачной среде нет пользовательского публичного preview для серверного стенда. Для просмотра без запуска Docker есть [скриншоты](SHOWCASE.md); для живого показа нужно запустить комплект на отдельной машине.

Проверка готовности после запуска провайдера:

```bash
curl --fail http://127.0.0.1:3280/health
```

### Если сборка использует корпоративный HTTPS-прокси

Подключить утверждённый CA как временный build secret, не отключать TLS:

```bash
docker build --secret id=build_ca,src=/путь/к/доверенному-ca.crt -t merch-selfhost-demo-app .
docker tag merch-selfhost-demo-app merch-selfhost-demo-setup
docker tag merch-selfhost-demo-app merch-selfhost-demo-retention
docker compose --env-file .local/demo.env up -d --no-build
```

### Тестовые пользователи

Пароль генерируется при первом `npm run init` в игнорируемом `.local/accounts.json`; значения не публиковать в репозитории.

| Логин | Доступ |
| --- | --- |
| alice | Получатель E-com |
| boris | Получатель Welcome pack Fintech |
| organizer | Супер администратор стенда, служебный аккаунт вне списка участников |
| fintech-admin | Только организация выдачи Fintech |
| dana | Новый сотрудник E-com: появляется в БД приложения только после разрешённого входа |
| elena | Новый сотрудник Fintech: для проверки группы/индивидуального допуска |
| outsider | Нет разрешения по умолчанию |
| blocked | Отключён в тестовом Keycloak |

Войти как organizer → «Тестовый почтовый ящик». Там ссылки корпоративных приглашений и гостевая ссылка. Гостевой идентификатор **TEST-GUEST-001**. Гостевую ссылку открывать в отдельном профиле/инкогнито, чтобы не заменить сессию организатора.

Для проверки QR можно использовать 2D-сканер с вводом как клавиатура. Защищённый API `/api/orders/{id}/receipt.json` позволяет владельцу/организатору получить тот же код для тестовой вставки в форму выдачи. Никаких личных данных в QR нет. Камерный сканер, PNG и массовая печать этикеток из основного приложения сюда ещё не перенесены.

## Допуск без HR-реестра

Войти как organizer → **«Доступ через портал»**. Выбрать раздачу E-com, тип «Юрлицо», TEST-ECOM, «Разрешить», «Основной каталог». В отдельном профиле браузера войти как **dana**: появится каталог E-com, хотя участник заранее не импортировался. Аналогично можно выбрать отдельного человека по ФИО/email или группу. Fintech-admin видит только свою часть тестового каталога и настраивает только Fintech. Роль администратора правилами получить нельзя.

Исключения сильнее разрешений. Противоречащие разрешения на разные магазины/разделы закрывают вход. После первого входа магазин/раздел не переносятся автоматически: изменение назначения требует проверки организатора, особенно при существующем заказе. Правила перепроверяются на сервере для каждого обращения; данные о юрлице/группах обновляются при повторной аутентификации, максимум через 15 минут без продления сессии. Старые явные разрешения реестра и служебные аккаунты сохранены отдельно; в новой чистой установке Alice/Boris представлены индивидуальными правилами.

Список людей — **фиксированный синтетический адаптер**, не настоящий каталог компании. Реальному поиску потребуется согласованный read-only API портала с ограниченным набором полей, пагинацией и областью видимости. Клиент не получает административный токен Keycloak. Правила сверяются с подписанными `legal_entity_code`, `merch_groups`, `employee_active`, а не со значениями формы/браузера. В настоящем провайдере эти атрибуты должны быть недоступны для самостоятельного редактирования сотрудником.

Если стенд уже запускался до появления этих claims, `npm run init -- --refresh-mock-realm` обновляет **только локальные файлы синтетического realm**, сохраняя секреты. Keycloak не обновляет импортированный realm автоматически: используйте новую отдельную тестовую установку либо осознанно сбросьте только свои синтетические volumes по процедуре ниже. Это не миграция корпоративного Keycloak.

## Welcome pack по личной почте

Organizer → «Доступы и приглашения» → «Новички без портала». Указать вымышленные ФИО, личную почту вида `newcomer@example.invalid`, раздачу и срок доступа (1–90 дней, по умолчанию 14). В тестовом почтовом ящике открыть персональное письмо в отдельном профиле браузера. Ссылка действует 20 минут: открытие страницы ещё не активирует её, требуется нажать «Войти в Welcome pack». Это снижает риск потребления ссылки почтовым предпросмотром. Проходят только заранее приглашённые адреса; пароль/Keycloak/табельный код не нужны.

Для следующего входа — `/email-login`, та же личная почта и новая ссылка. Ответ не раскрывает наличие приглашения, запросы ограничены по частоте. Новая ссылка заменяет прежнюю; её активация отзывает старые сессии, сохраняя аккаунт и заказ. Не запрашивать чаще раза в минуту, использовать последнее письмо. Сессия действует 15 минут; новый вход по почте доступен до получения, отзыва или окончания срока приглашения.

Только Welcome pack и очная раздача: основной каталог закрыт. Нельзя оформить второй неотменённый заказ. Отмена заказа не расходует право на получение. При выдаче транзакция вместе со списанием/статусом устанавливает `welcome_received_at`, выключает участника, удаляет его сессии, ссылки и тестовые письма. Старый QR/повторная выдача остаются безопасными; повторное приглашение того же профиля не открывает доступ заново. История остаётся у организатора до штатной очистки, пользователь после получения её не открывает.

Приглашение можно отозвать в той же форме. Истечение срока не отменяет заказ и не освобождает резерв: организатор должен продлить ещё не использованное приглашение либо отменить заказ. При продлении сохраняются прежние аккаунт/заказ. Отозванный или получивший мерч участник обычной повторной отправкой не активируется.

**Это новый серверный мок, не отправка настоящей почты:** ссылки хранятся в зашифрованном тестовом ящике организатора. Наличие доступа к письму здесь моделируется; настоящий SMTP, его очередь/повторы отправки и инфраструктурные ограничения нужно подключить отдельно. Реальные личные адреса в стенд не вводить. Передача персональной ссылки другому человеку даёт ему возможность войти: это стандартное подтверждение владения почтой, не привязка к устройству. Автоматического объединения с будущим корпоративным аккаунтом нет.

Запрет повторного получения действует в пределах сохраняемой записи участника. После её удаления политикой retention система не помнит получателя навсегда; долгосрочный учёт Welcome pack потребует отдельно согласованного кадрового/учётного источника и срока хранения. Произвольные разные email одного человека автоматически не распознаются как одна личность.

## Проверки

```bash
npm test
npm audit --omit=dev
```

Сквозной прогон требует **чистых синтетических volumes**. Он создаёт заказы, изменяет вымышленные остатки, закрывает раздачу, моделирует прошедший срок хранения и восстанавливает резервную копию именно этого стенда:

```bash
npx playwright install chromium
npm run test:portal
npm run test:welcome
npm run test:e2e
# Либо при наличии системного Chromium:
DEMO_CHROMIUM=/usr/bin/chromium npm run test:e2e
```

После сквозного прогона раздачи закрыты в результате проверки восстановления. Для нового показа сбросить **только этот Compose-проект**:

```bash
docker compose --env-file .local/demo.env down --volumes
docker compose --env-file .local/demo.env up -d --no-build
# Перезапустить npm run ports в другом терминале.
```

Это удаляет все тестовые записи, фотографии и журнал удалений текущего стенда. Старые `.local/backups` относятся к прежней installation и не восстанавливаются в новую. Не использовать эту процедуру для реальной БД.

## Резервная копия и восстановление

```bash
npm run backup
npm run restore -- --confirm-demo-only merch-selfhost-TIMESTAMP.mshbak
```

Копия содержит application DB и фотографии, зашифрована AES-256-GCM. Ключ — локальный тестовый `DEMO_BACKUP_KEY`, в Git не входит. Копии старше 7 дней удаляются **при следующем запуске backup**, не фоновым расписанием. Перед production нужны отдельные хранилище ключей, расписание копирования и контроль сроков.

Журнал удалений находится в отдельном volume и не откатывается вместе с БД. Restore сначала проверяет целостность, совместимость installation и наличие журнала, останавливает приложение, восстанавливает данные, отзывает старые сессии/приглашения и повторно применяет удаления. Раздачи остаются закрытыми: до их возобновления нужна сверка физических остатков и выдач, произошедших после точки восстановления. Автоматического production PITR здесь нет.
