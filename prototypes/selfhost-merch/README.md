# Merch Shop: серверный стенд корпоративного размещения

Обновлено 29 октября 2026. Это отдельный прототип на вымышленных данных. Рабочие Vercel/Supabase, реальный Keycloak, HR и SMTP не подключены и не изменены. Корпоративный сервер ещё не выделен. Стенд не заменяет production-приложение простой сменой URL.

Подробный контракт новых требований: **[LIFECYCLE.md](LIFECYCLE.md)**. Описание БД: [DATA-STORAGE.md](DATA-STORAGE.md). Эксплуатация: [OPERATIONS.md](OPERATIONS.md). Проверки: [VALIDATION.md](VALIDATION.md).

## Что работает

- Прямой OIDC Authorization Code + PKCE с отдельным тестовым Keycloak. ФИО, подтверждённая корпоративная почта, кадровые БЮ/юрлицо, необязательная дата удаления приходят от источника.
- Доступ по человеку, юрлицу или группе к одному магазину и разделу (каталог/Welcome pack). Офисный HR-реестр не нужен: участник создаётся при разрешённом входе. Поиск людей пока фиксированный синтетический адаптер.
- Подписанный кадровый API и интерфейс моделирования событий: немедленное удаление при получении события, будущая дата без нового входа, защита от повторов и восстановления удалённого пользователя из backup.
- Массовый персонал: импорт CSV (ФИО, юрлицо, должность, телефон, ПИНФЛ), персональная ссылка + сверка 14 цифр. ПИНФЛ хранится только как HMAC. Браузерная сессия на 30 дней, восстановление того же аккаунта через администратора. По решению пользователя автоматического источника увольнений массового персонала нет.
- Новички: персональная личная почта без Keycloak/пароля, одноразовая ссылка на 20 минут, повторный вход к тому же аккаунту. Реальные письма не отправляются: используется защищённый mock outbox.
- После выдачи или отметки отправки доступ участника закрывается, сессии отзываются. Через два календарных месяца по Asia/Tashkent удаляются его операционные ПД. Увольнение портального сотрудника обрабатывается раньше по событию.
- В PostgreSQL — каталог, типы, варианты, остатки и байты картинок. Администратор создаёт карточку с PNG/JPEG/WebP, размерами/цветами и количествами. Удаление людей не удаляет товары.
- Заказ до трёх разных товаров, по одной штуке, резерв/отмена, атомарная выдача QR, ручная фиксация отправки доставкой, безопасные повторы, количественный CSV и пороги остатка.
- Зашифрованные резервные копии и независимый журнал удаления. Метки журнала также требуют политики хранения; моментальное удаление старых архивов не обещается.

ФИО/корпоративный email/БЮ/юрлицо сохраняются в профиле; код юрлица/группы для допуска — в корпоративной сессии. ПД в снимок заказа не копируются. У массового персонала сохраняются телефон и должность из HR. Точного адреса доставки, телефона, свободного комментария и кадровых данных пользователь в заказ не вводит: доставка здесь согласуется отдельно, это не полный перенос shipping/PVZ рабочего сайта.

## Запуск

Node.js 24, Docker Engine + Compose v2. Использовать существующий checkout.

```bash
cd prototypes/selfhost-merch
npm ci --ignore-scripts
npm run init
chmod 644 scripts/init-db.sh
docker compose --env-file .local/demo.env up -d --build
```

При обновлении старой **синтетической** установки `npm run init -- --refresh-mock-realm` сохраняет секреты и обновляет файл тестового realm. Уже импортированный Keycloak сам его не перечитает: для полного обновления claims используйте новую тестовую установку либо осознанно сбросьте только свои mock volumes. Скрипт не меняет корпоративный Keycloak.

Если сборка требует доверенный CA среды, проверку TLS не отключать:

```bash
docker build --secret id=build_ca,src=/путь/к/доверенному-ca.crt -t merch-selfhost-demo-app -t merch-selfhost-demo-setup -t merch-selfhost-demo-retention .
docker compose --env-file .local/demo.env up -d --no-build
```

Во втором терминале `npm run ports`. Мост через `docker exec` слушает **только loopback**, приложение на 3280, тестовый Keycloak на 8280. БД не публикуется, Docker network — internal. После пересоздания app мост перезапустить. Это не пользовательский cloud preview и не production reverse proxy.

Пароль тестовых аккаунтов — в игнорируемом `.local/accounts.json`, секреты — `.local/demo.env`. Не печатать и не коммитить. Аккаунты: alice (E-com), boris (Welcome Fintech), organizer (super), fintech-admin (Fintech), dana/elena (новые участники без предварительного реестра), outsider (нет допуска), blocked (IdP выключен).

## Что показать

1. Organizer → «Доступы и приглашения»: правило по юрлицу/группе/человеку; отдельное приглашение новичка на вымышленную личную почту.
2. Organizer → «Кадровые события (мок)»: дата удаления, моделирование увольнения; HR CSV с заголовком `full_name;legal_entity;position;phone;pinfl`. Excel экспортируется в CSV UTF-8 с `;`, XLSX-парсер сюда ещё не перенесён.
3. Organizer → «Заказы и остатки»: создать товар/размеры/количества и картинку; собрать заказ. Офис — готовность и выдача по QR, доставка — «Отправили доставкой» после сборки.
4. Тестовый почтовый ящик организатора содержит персональные ссылки. Открывать в отдельном профиле браузера. Начальный старый гостевой seed для совместимости использует `TEST-GUEST-001`; новые HR-приглашения — ПИНФЛ из строки импорта. Реальные ПД не вводить.
5. После получения/отправки аккаунт участника больше не открывает каталог и историю. Администратор видит историю до срока удаления. Сроки можно моделировать в изолированной БД тестами; не менять часы рабочего сервиса.

Личная почтовая ссылка: открытие ещё не активирует её, требуется кнопка. Повторный вход `/email-login` не раскрывает наличие приглашения, ограничен по частоте, сохраняет аккаунт/заказ и отзывает старую сессию. Отзыв/получение не обходится повторной отправкой. Нет аппаратной привязки к устройству или автоматического объединения с будущим корпоративным аккаунтом.

## Проверки и сброс

```bash
npm test
DEMO_CHROMIUM=/usr/bin/chromium npm run test:portal
DEMO_CHROMIUM=/usr/bin/chromium npm run test:welcome
DEMO_CHROMIUM=/usr/bin/chromium npm run test:e2e
```

Отдельно, на **новой чистой** установке:

```bash
DEMO_CHROMIUM=/usr/bin/chromium npm run test:lifecycle
```

Сквозные сценарии меняют только синтетические данные, удаляют людей, закрывают раздачи и восстанавливают свой backup. После них стенд намеренно закрыт. Для нового показа — осознанный сброс **только своего Compose-проекта**:

```bash
docker compose --env-file .local/demo.env down --volumes
docker compose --env-file .local/demo.env up -d --no-build
```

Это уничтожает тестовые данные/журнал этой установки; старые архивы имеют другую installation и не подходят новой. Не использовать для корпоративной БД.

## Что ещё требуется

Реальный кадровый источник событий с надёжной доставкой/сверкой и согласованными claims; корпоративные PostgreSQL/HTTPS/секреты; SMTP; backup/PITR и график уничтожения копий/логов/служебных меток. Полное редактирование каталогов, офиса/текстов, PVZ, камера, массовая печать и другие функции рабочего приложения перенесены не полностью. Изменения сканирования рабочего сайта находятся отдельно в ветке `codex/confirm-order-handout` и не опубликованы без миграции.

## Защита и аудит

[SECURITY-CONTROLS.md](SECURITY-CONTROLS.md) разделяет реализованные меры и задачи инфраструктуры. HTTP-аудит API/авторизации выводится как JSON в stdout без тел, URL и токенов; X-Request-ID помогает сопоставить запрос. UUID исполнителя потенциально персональный. Docker-логи ограничены по объёму; корпоративный коллектор и сроки хранения ещё не настроены. СЗИ и production TLS не заменяются прототипом.
